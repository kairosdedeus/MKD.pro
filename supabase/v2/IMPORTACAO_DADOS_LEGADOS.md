# Importação opcional de dados legados para o MKD V2

> A V2 será construída em outro repositório e não terá compatibilidade de runtime com a V1. Este documento serve apenas para uma eventual importação única de dados selecionados.

## 1. Referência da simplificação

O modelo atual possui 26 tabelas distintas declaradas entre o schema principal e as migrations de funcionalidades. A V2 usa 16 tabelas.

| Área | Atual | V2 | Redução |
|---|---:|---:|---:|
| Usuários e perfis | 3 | 1 | 2 |
| Tipos, equipes, membros e funções | 5 | 4 | 1 |
| Escalas | 3 | 3 | 0 |
| Músicas | 2 | 2 | 0 |
| Equipes padrão e regras de rodízio | 6 | 2 | 4 |
| Células | 4 | 1 adicional (`Presenca`) | 3 |
| Notificações | 2 | 2 | 0 |
| Conteúdo do site | 1 | 1 | 0 |
| **Total** | **26*** | **16** | **10** |

\* O total considera tabelas criadas por migrations que podem não estar presentes em todas as instalações. No schema base há 20 tabelas; a conferência final deve ser feita em cada ambiente.

## 2. Tabelas mantidas por necessidade relacional

Não foi feita uma fusão indiscriminada. As tabelas abaixo continuam separadas porque representam relações muitos-para-muitos ou estado individual:

- `"EquipeMembroFuncao"`: um membro pode exercer várias funções.
- `"EscalaMembroFuncao"`: a função na escala pode ser diferente da função habitual.
- `"EscalaMusica"`: mantém ordem e tom de execução.
- `"NotificacaoDestinatario"`: leitura e dispensa variam por destinatário.
- `"EquipePadraoMembro"`: a mesma pessoa pode ocupar funções diferentes em presets.

Colocar esses dados em arrays JSON reduziria tabelas, mas perderia chaves estrangeiras, integridade e consultas simples. Esse trade-off não foi aceito.

## 4. IDs

### Regra

- Toda entidade do domínio usa `integer generated by default as identity`.
- O programador vê IDs como `1`, `2`, `153`, `2048`.
- `"Usuario"."AuthId"` continua UUID porque referencia `auth.users.id`.
- Storage continua usando caminhos de texto.

### Por que `integer`

`integer` ocupa 4 bytes, suporta mais de dois bilhões de valores positivos e é suficiente para o porte esperado do MKD. Também é representado naturalmente como `number` no TypeScript.

## 5. Padrão de nomes

| Elemento | Padrão | Exemplo |
|---|---|---|
| Tabela | Singular, substantivo, PascalCase | `"EquipeMembro"` |
| Coluna PK | `Id` | `"Id"` |
| Chave estrangeira | Entidade + `Id` | `"UsuarioId"` |
| Boolean | Pergunta/estado claro | `"Ativo"`, `"Gerencial"` |
| Data/hora | Ação + `Em` | `"CriadoEm"` |
| Unique | `UQ_Tabela_Campos` | `"UQ_EscalaMembro"` |
| Check | `CK_Tabela_Regra` | `"CK_Musica_Bpm"` |
| Index | `IX_Tabela_Campos` | `"IX_Escala_Equipe_Data"` |
| Trigger | `TR_Tabela_Acao` | `"TR_Escala_AtualizadoEm"` |
| Função SQL | Verbo em PascalCase | `"PodeGerenciarEquipe"` |

Não usar acentos em identificadores técnicos. Usar `Danca`, `Funcao` e `Configuracao`, mantendo acentos apenas nos textos exibidos ao usuário.

## 6. Padrão do código TypeScript V2

O código autoral novo será escrito em português do Brasil:

```ts
export interface Escala {
  id: number;
  equipeId: number;
  data: string;
  titulo: string | null;
  status: StatusEscala;
}

export async function buscarEscalasDoMes(
  equipeId: number,
  mes: Date,
): Promise<Escala[]> {
  // implementação
}
```

### Convenções

- Tipos, interfaces, classes e componentes: `PascalCase`.
- Funções e variáveis: `camelCase`.
- Ganchos React: prefixo técnico obrigatório `use` + nome em português, por exemplo `useEscalas`.
- Services: nomes de intenção, por exemplo `servicoDeEscalas`.
- Arquivos: `escala.servico.ts`, `escala.tipos.ts`, `DialogoCriarEscala.tsx`.
- Erros: `ErroDeValidacao`, `ErroDePermissao`.
- Não traduzir nomes de bibliotecas e APIs: `useQuery`, `Supabase`, `React`, `URL`, `JSON`.

### Exemplo de consulta

```ts
const { data, error } = await supabase
  .from("Escala")
  .select(`
    Id,
    Data,
    Titulo,
    Status,
    Equipe:EquipeId (
      Id,
      Nome,
      Ministerio
    )
  `)
  .eq("EquipeId", equipeId)
  .gte("Data", inicio)
  .lte("Data", fim)
  .order("Data");
```

## 7. Estratégia opcional de importação

### Fase 1 — banco novo

1. Criar o projeto Supabase vazio da V2.
2. Executar `schema_v2.sql`.
3. Gerar tipos TypeScript.
4. Copiar dados anonimizados.
5. Validar contagens e relações.

### Fase 2 — script de transformação

Criar tabelas temporárias de correspondência:

```text
MapaUsuario(UsuarioUuid, UsuarioId)
MapaEquipe(EquipeUuid, EquipeId)
MapaFuncao(FuncaoUuid, FuncaoId)
MapaMembro(MembroUuid, EquipeMembroId)
MapaEscala(EscalaUuid, EscalaId)
MapaMusica(MusicaUuid, MusicaId)
```

Esses mapas existem somente durante a migração e permitem converter todas as FKs UUID para integer de forma auditável.

### Fase 3 — aplicação independente

1. Desenvolver somente contra o schema V2.
2. Não criar adaptadores para nomes ou DTOs da V1.
3. Executar o importador fora do runtime da aplicação.
4. Comparar contagens e amostras.
5. Repetir a importação do zero até o resultado ser determinístico.

### Fase 4 — importação final, se necessária

1. Backup e teste de restauração.
2. Janela de manutenção.
3. Cópia final.
4. Validação automática de contagens, órfãos e checksums.
5. Publicação independente da V2.
6. Smoke test.
7. Preservar backup da V1 conforme a política de retenção.

### Fase 5 — encerramento do importador

O importador temporário só pode ser removido quando:

- a V2 estiver validada;
- as contagens foram aprovadas;
- auditoria e backup foram validados;
- não houver nova importação planejada.

## 8. Validações obrigatórias

- Nenhuma FK órfã.
- Nenhum UUID do domínio fora de `"Usuario"."AuthId"`.
- Um usuário gerencial mantém acesso completo.
- Líder acessa somente equipes que lidera.
- Membro acessa somente equipes em que está ativo.
- Escalas preservam membros, funções e músicas.
- Células preservam membros, encontros e presenças.
- Rodízio gera o mesmo resultado em meses de comparação.
- Notificações preservam leitura e dispensa.
- RLS é testada por ator e operação.
